# Spec coverage

Target: Matrix spec v1.19, default room version 12 (all versions 1–12 supported for joining).
Of v1.20, unreleased (the spec's changelog fragments as of 2026-11-28), what asks something of a
server is done: delayed events, sticky events, the `m.preview_url` and `m.delayed_events`
capabilities, `unsigned.prev_sender` (and v1.19's `unsigned.replaces_state`), `/relations` with `dir=f` from the oldest, non-negative
depths (scripts/v120test.py). v1.20 goes into `/versions` once it is released.
The conformance gate is Complement (`scripts/complement.sh`). The tests that fail by decision
are listed with their reasons in `tests/complement/expected-failures.txt` and skipped, so a
clean run exits 0 and every failure it reports is a real one; `COMPLEMENT_ALL=1` runs
everything. Last full run (2026-11-13): 207 top-level tests pass and none fail; the 12
expected failures (11 tests and one subtest) are skipped: 10 for features that are not
implemented, 2 deliberate deviations (see the end of this page).

| Policy servers (v1.18, MSC4284) | done for a homeserver in a room that uses one (asaroton is no policy server itself: `POST /_matrix/policy/v1/sign` is unrecognized here). A room uses one when its current state has a valid `m.room.policy` (empty state key, string `via`, string `public_keys.ed25519`) and `via` has a joined member; for every other room the cost is one lookup in the current state. Local events (messages, state, membership, redactions, invites, upgrades) are signed between being built and being stored: the policy server is asked with a signed federation request (5 s timeout), its `ed25519:policy_server` signature is checked against the room's key and added beside ours. A refusal the spec defines for `/sign` (400 `M_FORBIDDEN`/`M_BAD_JSON`/`M_NOT_JSON`, 403 `M_FORBIDDEN`, 404 `M_NOT_FOUND`/`M_UNRECOGNIZED`, 429 `M_LIMIT_EXCEEDED` with its wait capped at 60 s) reaches the client as it came; any other error answer becomes 403 `M_FORBIDDEN` with the policy server's message (a room's admins choose the policy server, and errcodes such as `M_UNKNOWN_TOKEN` make clients act); a signature that does not validate is a 403; unreachable, too slow or a server error, a 502. In every case the event is neither stored nor sent (no signature means not recommended; `m.room.policy` itself needs none, so a room can always drop a dead policy server). A room naming this server as its policy server gets a 403 saying so. A policy server that could not be reached is not asked again for 30 s. An invitation to another server is signed before it goes there; an upgrade asks about the tombstone before it makes the successor room; our join through another server goes out to the room's other servers only with the signature, asked for once the room's state is known. Received events (spec step 7): one without a valid signature is asked about once, and soft-failed when there is still none; a signature given then is stored with the event; backfilled history is not judged. As the resident server, `/send_join`, `/send_leave` and `/send_knock` ask first and fail with the policy server's error. Events looked at again after a rejoin, and soft-failed sticky events, are accepted only with a valid signature (not asked for). The policy key is never looked up as a server key (scripts/policytest.py). Not done: our own remote leaves and knocks (the room's state is not known), invitations from other servers received over `/invite`, asking again for events that were held back before step 7 (soft-failed on their auth, rejected, set aside) when they are accepted later, `/.well-known/matrix/policy_server` (served by policy servers). The room lock is held while the policy server is asked |

Known deviations (Complement): UIA accepts an `auth` dict without a session like Synapse does
(TestRegistration's strictness subtest, skipped for Synapse too); TestIsDirectFlagFederation sends
a room-version-12 invite without `m.room.create` in `invite_room_state`, which v1.16 (MSC4311)
requires receivers to reject (it passes on servers that still default to room version 11).
State resolution for room version 1 is approximated: where the room's history has diverged, the
newest state is taken instead of running the version 1 algorithm, which the state resolution
library does not implement. Only rooms created with version 1 and never upgraded are affected;
the server logs a warning when it comes to be in such a room and when the approximation is used.
